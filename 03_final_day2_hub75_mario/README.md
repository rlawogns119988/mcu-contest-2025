# 본선 2일차 — HUB75 LED 매트릭스 게임 (슈퍼마리오)

64x64 HUB75 RGB LED 매트릭스에 **동일한 게임을 두 개의 서로 다른 MCU로 각각 포팅**한 과제입니다.
같은 요구사항을 8비트 AVR과 32비트 ARM Cortex-M에서 구현하며 아키텍처별 제약 차이를 다뤘습니다.

| | Arduino (`arduino_atmega328p`) | STM32 (`stm32f4`) |
|---|---|---|
| MCU | ATmega328P @ 16MHz, 2KB SRAM | STM32F4 @ 84MHz (CubeMX 생성 골격 + 레지스터 직접 제어) |
| GPIO 제어 | `PORTB/PORTC/PORTD` 직접 write | `GPIOx->BSRR` (1사이클 set/reset) |
| 스프라이트 저장 | `PROGMEM` (플래시) → SRAM 절약 | 내부 플래시 상수 배열 |
| 사운드 | 타이머 인터럽트 사각파 | TIM4 (PSC=83 → 1MHz 카운트) 인터럽트 사각파 |
| 입력 | TM1650 키패드 (소프트 I2C, A4/A5) | TM1650 키패드 (소프트 I2C, PB6/PB7) |

## 핵심 구현

### HUB75 스캔 드라이버 (64x32 패널 2장 체인 = 64x64, 1/16 스캔)
HUB75는 한 번에 두 줄(상단 R1/G1/B1, 하단 R2/G2/B2)을 동시에 출력합니다.
행 주소 A~D(16행) → 128클럭 데이터 시프트 → LAT 래치 → OE 인에이블을 프레임 내내 반복하며,
잔상 없는 화면을 위해 이 루프가 **끊기지 않아야** 합니다.
HAL_GPIO_WritePin 같은 래퍼는 호출 오버헤드로 픽셀 클럭 타이밍을 맞출 수 없어 GPIO 레지스터를 직접 토글했습니다.

### 2KB SRAM에서 64x64 화면 구동
ATmega328P의 SRAM은 2KB라 64x64 프레임버퍼(최소 4KB 이상)를 담을 수 없습니다.
전체 프레임을 들고 있는 대신 **64바이트짜리 라인 버퍼 하나**(`displayBuffer[64]`)를 두고,
스캔 시점마다 해당 행의 픽셀을 게임 오브젝트 좌표에서 즉석 합성(`fillBuffer`)하는 방식으로 해결했습니다.

### BCM (Binary Code Modulation) 밝기 제어
3개 비트 플레인을 가중치(1:2:4) 시간 비율로 표시해 PWM 없이 계조를 표현했습니다.

### 연산량 최적화
- 마리오 점프 궤적을 `jumpArc[16]` 룩업테이블로 사전 계산 (실시간 물리 연산 제거)
- 스프라이트를 R/G 채널별 비트마스크(`uint16_t`)로 저장해 행 단위 비트연산으로 렌더링
- 오브젝트 수 상한 고정(굼바 6 / 박스 3 / 파편 8)으로 동적 할당 없이 정적 배열 운용
